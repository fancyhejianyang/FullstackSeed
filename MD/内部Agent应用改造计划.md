# 内部 Agent 应用改造计划

> 整理日期：2026-10-14
>
> 状态：T01～T11 已实施；T12 自动化自测已完成，目标环境数据库迁移、真实模型与人工 UI 验收待执行。
>
> 目标：将后台“AI 问答测试”升级为支持自然语言查询与受控录入的内部 Agent 应用。本文件同时记录业务、后端、UI、验收计划及实际实施状态；未勾选项仍需在目标环境完成。

## 一、改造目标与边界

用户通过自然语言表达需求，由 Agent 判断是回答、查询，还是准备录入，再调用受控的业务能力。不要求用户先切换“查询模式 / 录入模式”。

完整的 Harness 平台可以暂缓，但录入涉及的权限、确认、执行状态和防重复提交，是一期业务闭环的必要部分，不能只靠提示词约束。安全原则参考 [OWASP：Excessive Agency](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)。

### 1.1 三条处理路径

| 用户意图 | 系统处理 | 用户看到的结果 |
| --- | --- | --- |
| 知识问答 | 使用现有知识库和工作流 | 回答及资料来源 |
| 查询系统数据 | 识别对象、提取条件、调用授权查询工具 | 真实业务数据、摘要及详情入口 |
| 录入数据 | 识别字段、消除歧义、生成草稿、用户确认后提交 | 待确认表单，提交后返回记录编号和详情入口 |

例如：“先查一下有没有这个规格，没有就帮我新增。”应先查询；确认不存在后生成新增草稿，不能直接把“没有查到”当成允许落库的充分条件。

### 1.2 一期建议范围

- 先以产品 / SKU 查询和新增 SKU 作为试点，实际录入模块在开发前确认；不默认开放全部业务。
- 支持自然语言补充、纠正草稿，也支持手工修改字段。
- 暂不开放删除、批量修改、权限配置、任意 SQL 或任意接口调用。
- 保留现有工作流和外部客服能力，不把内部录入权限开放给外部聊天应用。
- 不以建设独立 Harness 平台、多智能体协作或长时间自主任务为一期前置条件。

### 2.1 权限边界

有效权限始终取以下交集：

**Agent 允许的能力 ∩ 当前员工的业务权限 ∩ 数据访问范围。**

通过 Agent 调用 Service 时，也不能绕过原先 Controller 承担的权限检查。用户身份由服务端登录态取得，不能由模型生成或由前端自由指定。

### 2.2 已落地契约

- 工具白名单：`knowledge.answer`、`product.query`、`productSku.create`；写入总开关关闭时服务端会移除写工具。
- 模型契约：Agent 直接保存 `providerId / providerName / models[]`，不依赖聊天配置；首个模型为主模型，调用失败时按数组顺序尝试备用模型，职责说明作为 Agent 系统提示词。
- 动作协议：`answer / query / clarify / prepare_write`。自然语言只产生结构化动作或草稿，不能直接触发正式写入。
- 草稿状态：`collecting / pending_confirmation / submitting / submitted / cancelled / expired / failed`。
- 执行状态：`queued / running / waiting_input / waiting_confirmation / submitting / verifying / succeeded / failed / cancelled`。
- SKU 草稿允许字段：`productId / skuCode / name / specifications / isEnabled`；必填为有效产品与至少一项规格。
- 确认契约：提交必须同时携带当前 `version` 与 `idempotencyKey`；草稿更新后版本递增，旧确认失效。
- 幂等契约：`product_skus.agentOperationKey` 保存服务端操作键并建立唯一索引；断线后可按 `requestId` 核实实际结果。
- 身份契约：会话、消息、草稿和执行记录均保存 `userId`；工作台接口只按服务端登录态读取本人数据。
- 权限码：管理端使用 `AgentApp.*`，员工工作台使用 `AgentWorkspace.read`，业务工具继续检查 `Product.read / ProductSku.read / ProductSku.create`。
- 数据范围：现有产品/SKU 模型没有租户、部门或负责人字段，因此一期范围为员工业务权限可见的全部未删除产品数据，查询只命中已启用记录；未来增加行级归属字段时，必须在工具 Service 中继续求交集。

主要接口：

- 管理：`/api/agent-apps`、`/api/agent-apps/configuration-options`、`/api/agent-apps/execution-records`。
- 工作台：`/api/agent-workspace/apps`、`/sessions`、`/sessions/:id/messages`、`/drafts/:id`、`/drafts/:id/confirm`、`/executions/:id`。

## 三、UI 设计方案

### 3.1 分成“应用管理”和“工作台”两个入口

Agent 应用管理面向管理员：

- 列表展示名称、用途、开放能力、使用范围、启停状态。
- 编辑表单直接选择模型账号和一个或多个模型，并配置知识工作流、查询工具和录入工具；单列布局确保标签和完整选项可读。
- 查询与写入能力分开展示，写工具明确标注“需要确认”。
- 提供调试入口，不默认向所有员工开放配置权限。

Agent 工作台面向实际使用者，不再要求每次填写模型账号、模型列表和工作流。

### 3.2 工作台布局

| 区域 | 设计内容 |
| --- | --- |
| 顶部 | 当前 Agent 名称、用途和可用能力；切换 Agent 时新建会话，原会话保留 |
| 左侧会话栏 | 新建会话、历史搜索、最近会话；窄屏时折叠 |
| 中间对话区 | 完整消息流、查询结果、追问、录入草稿和执行回执 |
| 底部输入区 | 多行输入、发送、停止；中文输入法选词时不误发送 |
| 按需详情面板 | 点击后查看来源、业务明细、草稿编辑或执行记录，默认不占据主区域 |

沿用现有后台主题、颜色和组件体系，不另造一套聊天视觉风格。

### 3.3 录入交互

录入卡片建议明确显示：

> **待确认：新增 SKU — 尚未保存**
>
> 所属产品：……
>
> 识别出的规格：……
>
> 需要补充：……
>
> 修改信息　确认录入　取消

关键交互规则：

- 用户说“颜色改成蓝色”，只修改当前草稿，不立即写库。
- 关联产品不唯一时，提供候选供用户选择。
- 草稿被修改后，旧版本确认失效。
- 提交成功后，原卡片变为只读回执，并提供“查看 SKU”。
- 失败时保留草稿，明确显示哪个字段或业务规则不满足。
- 网络超时显示“正在核实提交结果”，查询已有执行记录，不盲目重新创建。
- 已经提交成功的操作，不能因用户点击停止就显示“已取消”。

界面只展示可核实的执行状态和结果摘要，不展示模型内部推理。

### 3.4 组件复用

管理列表、配置表单和草稿编辑继续使用项目的 `PageContainer / Table / Form / Dialog / Button / Input / Select`。

只新增必要的业务展示组件，例如消息列表、查询结果卡、录入草稿卡和执行状态条。客服工作台的历史加载、会话切换防串响应等实现可以借鉴，但不直接复用其“外部访客 / 人工客服”的业务模型。

## 四、现有模块如何利用

### 4.1 AI 指令集

可复用现有白名单思路，但尚不能把它视为通用 Agent 执行器。现有写指令没有向聊天开放，内部 Agent 应增加独立的调用范围，不能简单打开外部聊天的写权限。

### 4.2 模块字段元数据

可辅助生成表单，但不能直接生成全库写工具。其中包含密码、管理员标志等字段，每个工具必须明确允许读写的字段，并复用真实 DTO 和业务校验。

### 4.3 审批模块

现有审批仅覆盖标准问答发布。普通录入的“本人确认提交”不等于业务审批；需要审批的业务仍按对应流程执行，不能以聊天中的一句“确认”代替审批人授权。

### 4.4 工作流与外部客服

现有知识问答工作流继续作为稳定的能力被复用，不必整体改成自主决策。内部 Agent 与外部客服保持身份、权限和写入范围隔离；已有外部客服的排队与人工接待机制不等于内部 Agent 已具备相同能力。

## 五、建议交付顺序

### 第一阶段：可用的内部查询助手（已完成）

完成 Agent 配置、身份隔离、完整聊天 UI 和查询闭环。

- 先明确 T01 的业务、字段和权限契约。
- 推进 T02～T05、T09，以及 T08、T10、T11 中支持只读运行所需的部分。
- 按 T12 验收只读能力，暂不开放正式业务写入。

### 第二阶段：一个业务的录入闭环（已完成）

完成自然语言提取、追问、草稿编辑、确认提交和真实回执。

- 在第一阶段基础上完成 T06～T07。
- 完成 T08、T10 中涉及写入状态、幂等、失败恢复和录入卡片的部分。
- 用一个经确认的代表性业务验证端到端流程。

### 第三阶段：验证后扩大能力（一期基础已完成）

验收重复提交、超时、权限变化等场景，再逐项增加其他录入工具。

- 完成 T11 的兼容迁移及 T12 的完整回归与 UI 检查。
- 通过配置逐项开放工具；发现问题时可以关闭写能力而保留查询。
- 其他录入模块、修改、删除、批量操作及更复杂的 Harness 能力，另行确认范围后实施。

## 六、首版验收目标

**员工不用知道系统字段名，也不用预先选择操作模式；Agent 能找对数据、问清缺项，并在明确确认后只录入一次正确的数据。**

- [x] 问答、业务查询、准备录入能正确区分；歧义或能力不足时主动说明或追问。
- [x] 查询回答基于实际返回数据，带有来源或业务记录入口，不虚构执行成功。
- [x] 无权限和跨用户会话访问被服务端拒绝。
- [x] 录入先形成草稿；自然语言补充与表单编辑均能更新同一草稿。
- [x] 确认前不写入正式业务数据；确认绑定当前草稿版本。
- [x] 重复点击、断线重试不造成重复业务记录。
- [x] 网络超时可以核实实际结果，已成功操作不会被误报为取消。
- [x] 外部客服与旧有工作流不因内部 Agent 写能力而扩大权限或出现功能回归。
- [x] UI 覆盖历史恢复、会话切换、候选选择、错误提示、窄屏和中文输入法场景。
- [ ] 在目标环境执行数据库迁移，并使用真实模型账号完成人工问答、查询、新增 SKU 和窄屏 UI 验收。
